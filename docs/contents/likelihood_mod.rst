.. _likelihood_module:

Likelihood module
#################

The :py:class:`asteca.Likelihood` class is used to define an object that can
compute how similar your observed cluster is, stored in
a :py:class:`asteca.Cluster` object, compared to a given
synthetic cluster, generated by the :py:meth:`asteca.Synthetic.generate` method.

This basically compares observed photometry versus synthetic photometry.

Currently, the only function implemented is the :ref:`plr`, as
described below. The user can of course choose to implement their own
likelihood functions, but this one is recommended because it is thoroughly tested,
well documented, and has been used in the literature. It is also
the one used in the examples and tutorials provided in this documentation.


To define a :py:class:`asteca.Likelihood` object, we need to provide a
:py:class:`asteca.Cluster` object which will be used to calibrate the likelihood
function:

.. code-block:: python

    # Define a likelihood object
    likelihood = asteca.Likelihood(my_cluster)

The likelihood compares the observed and synthetic clusters through their Hess diagrams
(the color-magnitude diagram split into cells). The ``bin_method`` argument selects how
the cells are defined, from the observed photometry:

- ``knuth`` (default), ``blocks``, ``scott``, ``freedman``: the number of bins in
  magnitude and in each color is set with the methods of the same name in
  `astropy <https://docs.astropy.org/en/stable/visualization/histogram.html>`_
- ``fixed``: 15 bins in magnitude and 10 bins in each color

In all cases the bins have equal widths and span the observed range of each
dimension.

.. code-block:: python

    # Define a likelihood object with a fixed binning
    likelihood = asteca.Likelihood(my_cluster, bin_method="fixed")

After this, we can compare a given synthetic cluster with the observed one. The
:py:class:`Likelihood <asteca.Likelihood>` object offers two methods for this, which
share the same core: one for distance-based samplers or optimizers (e.g.: ABC,
differential evolution) and one for likelihood-based samplers (e.g.: MCMC, sequential
Monte Carlo, nested sampling).

The :py:meth:`asteca.Likelihood.dist` method returns a **normalized and inverted**
likelihood, which serves as a distance measure between the observed and the synthetic
data:

.. code-block:: python

    # Generate an array with synthetic data, as described in previous sections
    synth_cluster_arr = synthcl.generate(params)

    # Distance between the observed and synthetic clusters
    dist = likelihood.dist(synth_cluster_arr)

The best value is ``0`` (exact match) and a value of ``1`` means that no synthetic star
falls in any of the observed bins. Synthetic clusters with no overlap get ``1`` plus a
penalty that grows with their photometric distance to the observed cluster, which
guides the samplers towards the region of the observed cluster, and empty synthetic
clusters get a distance of ``10``.

The :py:meth:`asteca.Likelihood.log_lkl` method returns the log-likelihood relative to
its maximum value (the observed cluster evaluated against itself), so that ``0`` is
again the best value:

.. code-block:: python

    # Log-likelihood of the synthetic cluster
    lnl = likelihood.log_lkl(synth_cluster_arr)

    # Tempered log-likelihood, which widens the posterior
    lnl = likelihood.log_lkl(synth_cluster_arr, temperature=2)

Its ``temperature`` argument divides the log-likelihood, which widens the posterior by
a factor of about :math:`\sqrt{T}`. Values larger than ``1`` can be used to account for
sources of uncertainty that are not included in the likelihood, such as the random
sampling of the synthetic clusters or the mismatch between the models and the observed
data. These dominate for clusters with many members, where a ``temperature`` of ``1``
gives uncertainties that are too small (see :ref:`paramfit_pocomc_ntbk` for an example).
No-overlap and empty synthetic clusters are given the log-likelihood that corresponds
to their distance, ``-dist * (max_lkl - min_lkl) / temperature``.



.. _ref_log_lkl_batch:

Log-likelihoods in batches
==========================

Some samplers evaluate many models at once, e.g.: pocoMC with ``vectorize=True``
passes all the particles of a step to the log-likelihood as a single array. For these,
the :py:meth:`asteca.Likelihood.log_lkl_batch` method takes a
:py:class:`asteca.Synthetic` object and a set of parameters per model, generates the
synthetic clusters, and returns an array with their log-likelihoods:

.. code-block:: python

    # Array x of shape (N_models, N_params), with the values of the parameters
    # in the list 'names'
    lnl = likelihood.log_lkl_batch(synthcl, dict(zip(names, x.T)), temperature=2)

The results are identical to calling
``likelihood.log_lkl(synthcl.generate(p), temperature)`` for each set of parameters
``p``, but the synthetic clusters are not returned. The ``synthcl`` object must be
calibrated with the same observed cluster used to define the ``likelihood`` object
(a ``ValueError`` is raised if it was not calibrated).
The parameters dictionary is defined as in :py:meth:`asteca.Synthetic.generate_batch`
(see :ref:`ref_generating_batch`): an array of values for each parameter, all with the
same length, or a single value shared by all the models; the parameters not included
take the default values of the ``synthcl`` object.

With `numba <https://numba.pydata.org/>`__ installed, the synthetic clusters and their
log-likelihoods are obtained in a single compiled call, which removes the Python
overhead of each model (the gain is largest for clusters with few stars).

.. important::

    **Without numba there is no speedup**: :py:meth:`asteca.Synthetic.generate` and
    :py:meth:`asteca.Likelihood.log_lkl` are called for each model, which is
    equivalent to (and as fast as) calling them in a loop. The code works the same in
    both cases.

With ``parallel=True`` the models are distributed among numba's threads: each thread
generates the synthetic clusters of its models and evaluates their log-likelihoods,
which also speeds up clusters with many stars, where the cost of each model is
dominated by the actual computation. The ``parallel`` argument is ignored if numba is
not installed.

.. code-block:: python

    # Evaluate the models in parallel threads, four threads for this call only
    lnl = likelihood.log_lkl_batch(
        synthcl, dict(zip(names, x.T)), temperature=2, parallel=True, n_threads=4
    )

The number of threads is set with ``n_threads``, for that call only. By default
(``n_threads=None``) numba's own setting is used, which is one thread per CPU core
unless changed with the ``NUMBA_NUM_THREADS`` environment variable (set before
importing ``asteca``) or with ``numba.set_num_threads()``; ``n_threads`` can not be
larger than ``NUMBA_NUM_THREADS``. If several fits are run at the same time, give each
one a fraction of the CPU cores so that they do not compete for them. Each thread
needs several models per call to be used efficiently, so the batch should be larger
than the number of threads (for pocoMC the batch is ``n_active`` particles).

See the :ref:`paramfit_pocomc_ntbk` notebook for a complete example.




.. _plr:


Poisson likelihood ratio
========================


This is the Poisson likelihood ratio as defined in `Tremmel et al (2013)`_. Starting
from Eq 10 with :math:`v_{i,j}=1` (i.e.: equal volumes for all cells), we have:

.. math::

    p(d|\theta) = \prod_i^B \frac{\Gamma(n_i+m_i+\frac{1}{2})}
    {2^{n_i+m_i+\frac{1}{2}} n_i!\Gamma(m_i+\frac{1}{2})}

where :math:`n_i` and :math:`m_i` are the number of observed and synthetic stars in 
bin :math:`i`, respectively, and :math:`B` is the total number of bins.
Applying the logarithm:

.. math::

    \log(p) = \sum_i^B \left[\log\Gamma(n_i+m_i+\frac{1}{2})
    - (m_i+n_i+\frac{1}{2})\log2 -\log n_i!
    - \log \Gamma(m_i+\frac{1}{2}) \right]

re-arranging:

.. math::

    \log(p) = \sum_i^B \left[\log\Gamma(n_i+m_i+\frac{1}{2})-
    \log \Gamma(m_i+\frac{1}{2}) \right]
    - (M+N+\frac{1}{2}B) \log 2 - \sum_i^B \log n_i!

employing the :math:`LogGamma()` function;

.. math::

    \log(p) = \sum_i^B \left[LogGamma(n_i+m_i+\frac{1}{2}) - LogGamma(m_i+\frac{1}{2}) \right] - \\ (N+\frac{1}{2}B) \log 2 - \sum_i^B \log n_i! -M  \log 2

.. note::

    The :math:`LogGamma()` function is used instead of the :math:`\Gamma()`
    function because it is numerically more stable, especially when
    dealing with large numbers. This is implemented in `scipy.special.gammaln`_.


We can discard the second and third terms as they depend on :math:`N` and :math:`B`
only (i.e.: the number of stars in observed cluster and the number of bins), and hence
do not change for different synthetic data.

The last term depends on :math:`M`, the total number of synthetic stars. Once the
:py:class:`asteca.Synthetic` object is calibrated, every synthetic cluster generated
by :py:meth:`asteca.Synthetic.generate` contains the same number of stars as the
observed cluster (with valid photometry), i.e.: :math:`M=N` (except in the case
described below), and this term is a constant that can also be discarded.

.. important::

    A synthetic cluster can contain fewer stars than the observed one
    (:math:`M<N`) only when the IMF sample (see the ``max_mass`` argument of
    :py:class:`asteca.Synthetic`) can not provide enough stars brighter than the
    maximum observed magnitude. This only happens for models far from the observed
    cluster (e.g.: too distant or too old), which have a large distance with or
    without this term.

Finally, discarding the last three terms, we have the expression for the Poisson
likelihood ratio:

.. math::

    \log(p)\approx \sum_i^B \left[LogGamma(n_i+m_i+\frac{1}{2}) - LogGamma(m_i+\frac{1}{2}) \right]


This likelihood is normalized and inverted so that the best value is ``0`` and the
worst value is ``1``, as mentioned above:

.. math::

    d = \frac{\log(p)_{max} - \log(p)}{\log(p)_{max} - \log(p)_{min}}

where :math:`\log(p)_{max}` is the value obtained comparing the observed cluster with
itself (:math:`m_i=n_i`), and :math:`\log(p)_{min}` is the value obtained when no
synthetic star falls in any of the bins occupied by observed stars (:math:`m_i=0`).
Hence :math:`d=0` means an exact match, and :math:`d=1` means that the synthetic and
observed clusters do not overlap at all in the CMD. This puts the end points of the
distance on the same scale for all clusters, but the values in between are still not
comparable across clusters: the distance obtained for a correct model depends on the
number of stars and on the binning (see :ref:`cmd_overlap`).

When the synthetic and observed clusters do not overlap at all, the likelihood takes
the same value regardless of where the synthetic stars are located in the CMD. To
break this tie, which can stall the parameter fit when most models sampled from the
priors have no overlap (e.g.: for small clusters), the distance for these models is
set to:

.. math::

    d = 1 + \left(\frac{\tilde{G}_{obs} - \tilde{G}_{syn}}{\Delta G}\right)^2 +
    \left(\frac{\tilde{C}_{obs} - \tilde{C}_{syn}}{\Delta C}\right)^2

where :math:`\tilde{G}` and :math:`\tilde{C}` are the median magnitude and color of
the observed and synthetic clusters, and :math:`\Delta G` and :math:`\Delta C` are the
widths of the magnitude and color ranges of the observed Hess diagram. The latter
put both dimensions on the same scale, so that the magnitude (which usually spans a
much larger range) does not dominate over the color. Hence any synthetic cluster with
some overlap (:math:`d<1`) is always considered better than any synthetic cluster with
no overlap (:math:`d\geq 1`), and the latter are pulled towards the region of the
CMD where the observed cluster is located.

Synthetic clusters with no stars (e.g.: parameters that place the whole isochrone below
the maximum magnitude of the observed cluster) are assigned a fixed distance of
:math:`d=10`, so that they are always considered worse than synthetic clusters with
stars (unless these have medians several Hess diagram widths away from the observed
cluster).


.. _cmd_overlap:

Goodness of fit
===============

The distance returned by :py:meth:`asteca.Likelihood.dist` is useful to compare
synthetic clusters for the *same* observed cluster, but its value can not be compared
across clusters: even a perfect model gives :math:`d>0` because of the finite number of
stars, and this "noise floor" depends on the number of stars and on the binning of the
Hess diagram.

To assess whether a given synthetic cluster (e.g.: generated with the best fit
parameters) is a good representation of the observed cluster, the
:py:meth:`asteca.Likelihood.cmd_overlap` method can be used:

.. code-block:: python

    synth_cluster_arr = synthcl.generate(best_fit_params)
    D, D_std = likelihood.cmd_overlap(synth_cluster_arr)

The first value returned is:

.. math::

    D = 1 - \frac{2\,K_{os}}{K_{oo} + K_{ss}}

where :math:`K_{os}` is the mean value of a Gaussian kernel over all the pairs of
observed and synthetic stars, and :math:`K_{oo}` and :math:`K_{ss}` are the mean values
over all the pairs of *distinct* observed stars and of distinct synthetic stars. The
kernel for two stars separated by :math:`(\Delta G, \Delta C)` in magnitude and color
is:

.. math::

    k = \exp\left[-\frac{1}{4}\left(\frac{\Delta G^2}{h_G^2} +
    \frac{\Delta C^2}{h_C^2}\right)\right]

with :math:`h_G=0.3` and :math:`h_C=0.075` mag by default. :math:`D` is the squared
difference between the observed and synthetic densities in the CMD, both smoothed with
a Gaussian of widths :math:`(h_G, h_C)`, normalized so that :math:`D=0` means the same
distribution and :math:`D=1` means no overlap. In other words: for each star it
compares the fraction of the synthetic cluster located around it (within the kernel
widths) with the fraction of the observed cluster.

Two properties make :math:`D` comparable across clusters with very different numbers
of stars:

- Stars are never compared with themselves (:math:`K_{oo}` and :math:`K_{ss}` exclude
  the pairs of a star with itself). Hence a synthetic cluster drawn from the same
  distribution as the observed one gives :math:`D=0` on average for any number of
  stars. Individual values fluctuate around ``0`` (and can be negative) by an amount
  that decreases with the number of stars
- The kernel widths, i.e.: the scale at which the CMDs are compared, are fixed and do
  not depend on the number of stars. Hence a given mismatch gives on average the same
  :math:`D` for any number of stars

In tests with simulated clusters a value of :math:`D\leq 0.25` was found to be
a reasonable general threshold for a good fit; for clusters with many stars a
stricter threshold can be used.

The second value returned, ``D_std``, is the approximate standard deviation of
:math:`D` for a synthetic cluster drawn from the same distribution as the observed one
(i.e.: a correct model). It decreases with the number of stars and gives the size of
the fluctuations expected by chance alone. If the synthetic cluster has fewer than two
stars, ``D=1`` and ``D_std=0`` are returned.

Notes:

- Negative values are expected and are **not** clipped to ``0``. They only mean that,
  by chance, the synthetic cluster matches the observed one slightly better than the
  average correct model, i.e.: :math:`D<0` is a match within the noise. A value of
  e.g. :math:`D=-0.03` with a standard deviation of ``0.05`` is fully consistent with
  :math:`D=0`. Clipping would bias the average of :math:`D` upwards (more so for
  small clusters), which is precisely what excluding the self-pairs avoids. Including
  the self-pairs instead would make :math:`D\geq 0` always, but then even a correct
  model would give larger values for smaller clusters, and :math:`D` could no longer
  be compared across clusters
- The same kernel widths must be used for all the clusters whose :math:`D` values are
  compared
- :math:`D` is dominated by the most populated regions of the CMD. Sparse field
  contaminants have a very small effect on it, but differences in sparsely populated
  regions (e.g.: a turn-off or a few giants) also contribute little
